# CoursePlan 开发日志、技术说明与挑战复盘

整理日期：2026-11-03。依据本次完整对话中的需求演进、当前源码、LOCAL-CHANGES.md 及可核验的测试记录整理。早期消息未提供可靠日期的阶段，按对话顺序记录，不补造工时、提交历史或执行结果。本文件是一份开发过程复盘，不是聊天逐字稿，不包含账号、令牌、学号、密码和私人数据库内容。

## 一、项目目标与当前成果

项目从少量本地手工课程资料和初版学期规划界面，逐步发展为支持多个 Program、完整课程依赖浏览、个人学分目标、计划管理、本地账号、Ollama 向量 RAG 与约束求解的课程规划原型。

目前整理的官方 2024 历史课程共178门：信息技术 C10148 65门、视觉传达设计 C10308 61门、商科 C10026 52门。每个 Program 有独立数据集、课程池、档案与计划。178门是候选目录，不代表每位学生需要修完，也不是当前学年开课保证。

完整应用在本地 Node 服务中运行。GitHub Pages 是明确标示的静态演示，提供 Guest、课程目录、依赖图、手动学期安排、学分统计、导入导出、浏览器保存和关键词推荐；账号登录、Python自动规划、Ollama生成与向量检索需要本地服务，线上不伪造这些能力。

## 二、按对话顺序整理的开发日志

### 阶段1：审视原课程规划项目与数据源

用户最初请求评估 GitHub 上的课程规划系统，随后明确首要问题是数据：现有资料少、手工查找后放在后端，没有传统数据库，希望引入数据库并连接 UTS 课程接口，至少记录先修关系。

讨论了官方API批准、公开手册抓取、外部结构化样本及人工模拟等路径。数据策略逐步收敛到优先使用官方可追溯资料，无法获批API时使用公开历史手册；模拟数据必须显式标明，不能冒充学校规则。早期对话涉及8门种子课/少量类别，其范围不能代表学校全部专业或先修资料。

用户创建 Supabase 的 CoursePlan 项目，完成后台登录、项目定位和SQL结构查看。开发中也解释了项目后台链接与公开数据库接口的区别。当前代码能选配只读 Supabase catalog_subjects 视图，但本仓库没有完整云端DDL迁移记录，不能据对话中的“已连接”推断所有数据已同步到云端。

### 阶段2：采用 UTS Handbook 历史资料

用户希望尽可能抓取 UTS Handbook，并控制学科规模。以官方2024历史页面为基础，分离科目编号、名称、学分、先修/共修、互斥、描述及开课资料，保存来源链接和原始条件。

数据不足或条件无法可靠判断时保留 unknown/manual；没有列出学术先修的页面，在核对后显式记录空条件，同时继续提示专业准入另行确认。没有把抓取失败等同于学校没有这门课，也没有通过规避访问限制来伪装实时API。

### 阶段3：参考 Circles 项目改善信息架构

用户提出参考 Circles360/Circles360.github.io，希望界面更正式直观。迭代重点是课程目录、依赖图、学期安排、右侧详情和计划检查的联动，并保留适合自身数据和规则的实现。此次对话不构成已复制第三方代码或资产的证据。

用户要求先留在本地预览，不推送和上线。此后一直通过 localhost:3010 验证，直到本次明确提出发布新仓库才开始准备 GitHub 版本。

### 阶段4：计划管理与 AI 入口迭代

补充新建、切换、删除与恢复计划，删除进入可恢复列表；导出JSON用于备份。增加撤销和计划校验，导入时拒绝不匹配的数据集与重复课程编号。

用户多次反馈看不到AI推荐入口。AI由课程详情中的较隐蔽位置改为独立标签，与学期安排并列，减少查找成本。解释了连接生成模型与RAG并不冲突：检索负责提供相关课程和证据，模型负责在候选中选择、排序，而不是独立编造课程。

### 阶段5：本地 Ollama 与向量 RAG

用户要求接入本地 Ollama 和向量检索；考虑磁盘容量，把项目、运行资源和模型集中到D盘。用户在本机执行启动脚本并确认“Ollama started”。

实际采用 qwen3:1.7b 作为生成模型，EmbeddingGemma 作为向量模型，向量维数768。查询经中英词义扩展后嵌入，以余弦相似度检索当前Program课程，再把候选与来源交给生成模型。索引按模型摘要及课程内容指纹缓存到.rag-index，课程变化会重建。

用户用“我想学做菜”、拼写不完整的“我想学zuo'cau”等问题测试，并看到“仅课程检索/未使用生成模型”。复盘时应区分目录无相关课程、输入匹配不足、向量或生成服务不可用等情况；不能因界面有AI标签就宣称每次都完成了模型生成。

小模型曾可能生成无依据的课程内容或资格解释，因而对输出限定候选编号、证据ID及可核验理由模板。资格由独立规则引擎判断。该RAG的生成自由度有限，优先保证有出处与不捏造。

### 阶段6：课程简介与暗色视觉

用户希望推荐卡片和右侧详情提供快速理解的简介。整理官方Description的中文摘要或英文原文节选，显示来源与年份；按用户要求把“一句话简介”改为“简介”。推荐依据和课程简介分别表达用途。

参考用户提供的紫色科技感图片，界面调整为深蓝紫底色、紫青渐变边框、柔光、清晰状态色，并放大课程代号。新增选修课程未全部翻译为中文，保留明确标识的官方英文节选，避免把未审核译文作为事实。

### 阶段7：登录、Guest、档案与多 Program

实现本地邮箱注册/登录与免注册Guest。用户档案包含称呼、Program、入学年份、可选学号、目标CP和认可/转入学分。它是应用本地账号，不是UTS校园认证或SSO。

账号资料与计划存入SQLite；Guest保存在浏览器。账号、Program与数据集共同限定存储范围，避免Art课程混入IT，或跨专业导入错误计划。已完成、认可、已规划、尚需完成和未规划学分分别统计；规划课程不会在尚未通过时计入已完成。

最初IT16门、设计14门、商科8门，为后续扩充建立多专业结构。商科、设计的图例、课程、详情与AI均跟随Program切换。

### 阶段8：学期卡片操作与年份

用户反馈移除已排课程只能到右侧详情操作。学期卡片新增独立删除按钮，移出后返回目录未安排状态，保留拖拽手柄，并复用撤销和持久化流程。

安排学期的范围按用户反馈最终确定为2024—2030的Autumn/Spring。选择新学期只用于预览，实际加入课程时再创建，避免浏览下拉框就产生空学期；已有范围外学期仍保留。

### 阶段9：目标学分与多方案规划

用户提出按个人学分要求推荐可选择的课程路径，同时担心课程池不足。实现“路径方案”面板，最多生成三种不同方案：尽早结束、学分均衡、兴趣优先/不同选修组合。没有试图枚举所有组合，因为课程选择与学期排列会快速膨胀。

设置项包含累计目标、起始学期、负载上限、兴趣、保留已有安排、必选/排除、严格历史开课和认可课程映射。采用方案会新建计划而保留原计划。规划元数据记录规则版本、目标、生成时间、认可映射和手动修改标记；修改后提示重算。

先补充设计相关选修47门，设计14→61门，尝试结构化144CP路线。发现C10308正文写108+24+12，而结构化完成要求及模块页对应108+18+18；当前采用后者的明确草案，拆为108核心+18 Design Studies+12设计选修+6跨学科。界面保留冲突说明、历史版本提示与确认，不作为校方毕业批准。

认可学分不能重复安排或同时计入已修。毕业草案需把认可CP映射到具体课程，多模块科目需明确计入哪个模块，同一课只计一次。

### 阶段10：修复“总是没有新方案”的数据不足

用户实际使用后反馈不能生成。代码发现默认阶段目标通常144CP，而IT原始目录最多只有96CP、商科只有48CP，且还存在互斥、缺失先修和开课条件，仅修改目标提示不足以满足用户意图。

用户要求真正扩充课程。抓取IT核心和5方向课程池，以及商科核心、金融、管理、市场营销课程池：IT16→65，商科8→52，合计新增93门，设计保持61门，全站178门。

解析AND/OR、括号、c共修标记及符合当前Program的最低学分条件。来源括号错误或特定Program学分解释采用经过核对的显式表达式，并绑定原文SHA256；原文变化时回退人工核验。主修模块学分不能被全局CP代替；7门无法自动证明的学术条件保留manual。重新核对了Programming 1与Programming Fundamentals互斥，避免等价课凑学分。

三个Program都实际验证了从零累计144CP的阶段方案：例子中尽早结束6个安排学期、峰值24CP，均衡8学期、峰值18CP。结果依赖历史开课与已标明假设；IT/商科仍未完整建模毕业主修组合，144CP阶段达标不等于毕业审核通过。

### 阶段11：完善完整课程路径图

用户发现目录多而图少。原因是原图仍使用精选课程的手工坐标。替换为全目录自动布局，支持IT65、商科52、设计61门全部视图；默认核心，按官方方向筛选，自动补入先修上下文。

实现搜索定位、右侧详情联动、递归先修与后续链高亮、仅看当前链、计划/完成/RPL状态、缩放和适应全图。布局使用Tarjan强连通分量处理循环和共修，再在压缩DAG按依赖分层，按前驱位置排序；同层过多则横向分列，避免纵向无限拉长。未收录的历史替代编号列出提醒，不伪造课程。

浏览器核对三个Program全部节点数量，41026新课程搜索、详情和4节点聚焦链正常；页面无横向溢出或控制台错误。

### 阶段12：发布新仓库与静态演示

用户本次明确授权把当前项目发布到GitHub，保留原uts-course-planner。新版本最初以courseplan-ai创建，随后按用户要求重命名为courseplan，并同步更新演示路径、文档与配置。发布采用完整源码加独立静态演示，而不是覆盖旧仓库。

为Pages增加静态模式：Guest、计划管理、图、拖拽和基础推荐可在浏览器运行；不调用不存在的账号、求解或Ollama接口，清楚说明线上推荐是关键词匹配。静态构建在隔离目录完成，不移动或删除完整应用API源码，也不触碰正在运行的本地账号数据库。

发布前排除.env.local、SQLite账号/会话、模型、向量缓存、虚拟环境、依赖、原始抓取缓存和临时测试数据，更新README与运行步骤。发布结果以GitHub仓库与Pages部署状态为准，单纯提交工作流不等同于网站已经上线。

## 三、当前实际使用的技术

### 前端与交互

Next.js15.5.27 App Router、React19.1.8、TypeScript5负责页面与类型。主要入口为AppPortal、PlannerWorkspace、CourseGraph、PathwayPanel和GroundedRecommendations。@dnd-kit处理学期拖拽、碰撞和键盘传感器；Lucide React提供图标。CSS自定义属性、Grid/Flex、渐变和响应式样式构成当前视觉，Tailwind CSS3.4/PostCSS参与构建。

当前关系图是HTML按钮节点加SVG连线、独立的TypeScript图算法，并非D3力导向图。仓库历史组件/依赖还包括D3、react-force-graph-2d、Ant Design Icons、date-fns等，不能据package.json把它们都说成当前主界面的核心实现。

### 服务端、身份与存储

Node.js>=22.13提供原生node:sqlite；项目本机使用Node22系列。Next Route Handlers提供auth/profile/workspace/catalog/ai-status/recommend-grounded/pathways接口。

账号采用scrypt加盐哈希、随机会话、令牌SHA256、HttpOnly Cookie、会话有效期、来源/JSON检查及登录失败限流。SQLite的users、sessions、workspaces、login_limits表保存本地账号与工作区。LocalStorage负责Guest和账号本地备份，JSON负责计划导入导出。

Supabase提供可选PostgreSQL课程目录访问，通过REST只读视图读取。当前主要可复现课程快照是版本化JSON；旧云端子集与已核对本地扩充目录合并，避免从65门退回16门。Supabase不承担当前本地账号认证，项目没有宣称使用Supabase Auth或pgvector。

### 数据采集与规则

Python标准库urllib.request、html、re、json、pathlib及有限并发负责采集/缓存/清洗；原始资料来自UTS Handbook2024。导入脚本把学术条件转为subject/all/any/credits/manual表达式，保留原始文字、来源、审核状态和开课信息。手册访问在受限网络下使用本机可用代理，发布脚本允许配置代理，不关闭TLS验证。

### 本地AI与RAG

Ollama提供本地HTTP推理；qwen3:1.7b负责受约束候选选择，EmbeddingGemma生成768维向量。实现余弦相似度、阈值过滤、已修/已排排除、中英词义扩展、每Program独立索引、模型与文档内容指纹及原子缓存写入。向量存储是本地JSON索引，不是外部向量数据库。

服务异常时区分无匹配、关键词回退、向量检索与生成成功。模型输出经过课程白名单、证据ID和理由约束校验；学术资格仍由确定性规则判断。

### 自动规划

Python3.10+与OR-Tools9.14.6206 CP-SAT负责组合优化。本机Python3.13，依赖位于.planner-venv。Node以隐藏窗口子进程通过JSON标准输入输出调用，设置并发与超时限制。

布尔变量表示课程是否在学期修读；硬约束覆盖唯一性、精确目标、先修/共修、互斥、负载、开课、已有锁定、认可和模块分配。软目标比较结束时间、峰值负载、兴趣和选修差异。独立audit复算结果，区分可行解、已证最优、超时、资料不足与约束冲突。

### 构建、测试与发布

npm与package-lock.json用于可复现安装，TypeScript检查、ESLint、Node内置node:test和Python unittest负责验证。本轮图功能完成时有29项Node测试、22项Python测试；本次发布适配亦已通过完整应用构建、独立Pages静态导出与浏览器Guest/排课/关键词推荐验证，静态预览没有请求后端API。

Git保存源码，GitHub新仓库与GitHub Pages承载公开版本，GitHub Actions负责安装、测试、静态构建及发布。Windows PowerShell用于本地脚本与服务管理，启动服务使用隐藏窗口。模型文件、虚拟环境和账号数据库不进入Git。

## 四、开发难点与处理方式

1. **没有获批实时课程API**：转向官方历史资料，版本与来源随课程保存；不能把抓取快照包装成实时API。
2. **先修规则比一条箭头复杂**：保留AND/OR、共修和最低学分；未知条件显式待核验。全图展示引用，资格另算，避免把所有替代路径误当必修。
3. **课程数或CP总和够但仍无解**：补齐可达先修链、互斥和开课资料，并用实际求解验证，不只累加目录CP。
4. **官方文本内部冲突**：设计144CP分配不一致，保留草案、冲突与确认流程，避免偷偷选择一个版本当作权威。
5. **大模型幻觉与弱匹配**：候选白名单、证据绑定、有限理由模板、中英词义扩展和无匹配退出共同约束；不让模型决定毕业要求。
6. **用户分不清模型是否工作**：把模型状态、检索方式和回退原因分开显示；静态在线版明确不调用模型。
7. **跨专业与重复计分**：数据集/Program边界、导入校验、同课模块唯一归属和RPL映射防止混课与双计。
8. **扩充目录后图仍停留旧子集**：去掉手工坐标，以全目录图算法和方向筛选保证覆盖；SCC、分层与分列处理循环和规模增长。
9. **操作入口不直观**：AI独立标签、卡片直接移除、简介、用户信息和CP进度让常用操作可见。
10. **个人电脑资源限制**：集中D盘、选择较小模型、缓存索引、限制求解时间；不把本机Ollama暴露给互联网。
11. **静态托管无法运行后端**：隔离静态构建，明确Guest/关键词模式；完整源码保留Node/Python/RAG，不用虚假生成结果冒充在线服务。
12. **发布可复现性与历史配置遗留**：清理重复PostCSS版本配置、更新过期README/模型名/basePath、排除构建与运行目录，并分别验证本地与Pages构建。

## 五、目前边界与后续方向

需要继续确认适用入学年份、最新开课、专业准入、学分认可和正式培养模块。IT/商科的阶段144CP方案不是完整毕业路径；设计规则仍有已知分配冲突。公开手册的使用与再分发应保留学校来源及权利声明。

下一步可优先做培养方案版本化、主修选择与模块配额建模、学校认可的RPL流程、课程数据增量同步及变更审查。若要让公网用户使用账号、自动规划与RAG，需要另行部署可信服务端、持久化数据库及合适的模型推理资源；GitHub Pages本身不能提供这些服务。
